# 左右手独立实现接入工作台

本次集成以已经调试的独立程序提交
`eaafec6bb0cce77b7fb7019c9f828d5afb97950a` 为行为基线，工作台基线为
`7f7fccae0c2e077d8291723039248a264e9f1c3f`。开发分支为
`codex/integrate-hand-runtime-workbench`。

## 入口与职责

工作台不增加“手套”工作区。选中原有左手或右手姿态/触觉设备，主预览区域显示该手的共享三维面板；原有标定按钮展开同一个面板内的动作示范、实时手势和采集反馈。相机预览、VIVE Hub、联合空间及点云仍使用原来的工作区和控制入口。

| 层 | 当前实现和唯一职责 |
| --- | --- |
| 数值核心 | `tools/fsglove12`：复用独立程序的读取、融合、安装标定、功能标定、形状/触指及 MANO 解算；工作台不重新计算角度。 |
| 手部服务 | `vt_fsglove12.hand_service`：每手一个无 GUI 服务，使用原 `ProcessLiveController`。数值运行于该手明确配置的 Python 环境。 |
| 设备管理 | `vt_capture_manager.hand_control` 与 `ProcessSupervisor`：统一启停、资源归属、命令回执与录制准入；界面不另开 IMU 串口。 |
| 姿态录制 | 原 `vt_glove_bridge` 消费同一服务发布的姿态。示范动画、显示保持和触觉颜色不进入姿态测量。 |
| 触觉采集 | `vt_tactile_capture`：每手一个 44 字节行协议读取器，发布原始样本、完整状态和只读显示数据。 |
| 触觉展示 | `ManagedTactileSource` 消费完整状态，复用独立程序的参考、响应和配色。不打开串口，不复用抽稀的设备卡片缩略图作输入。 |
| 共享界面 | `vt_capture_console.ui.hand`：工作台与 `vt_hand_tactile_viewer` 使用同一个面板、显示合成和标定动作定义。独立入口只负责自己的启动与资源装配。 |

切换预览只切换展示，缓存的手部订阅仍可继续更新；关闭工作台只分离显示订阅，不断开正在运行的服务或录制。
显式设备停止操作由管理器执行。独立程序仍拥有自己启动的设备，不能与工作台同时读取同一串口。

## 配置与部署

每个 `glove` profile 使用 `hand`、`glove_python`、`port` 和 `resources`。
`resources` 是对应独立程序的完整资源包，包含 `manifest.json`、配置、静态手形、MANO 模型、上游固定源码，以及左手明确指定的触觉布局。清单哈希和手别在加载前校验。

为兼容显式维护的配置，也支持 `fsglove_source`、`mano_assets`、`config`、`rest` 四项代替资源包；缺少任何一项会在配置或启动预检中明确拒绝，不再等子进程启动才失败。`rest` 是该安装对应的静态手形参考，不能从其他安装猜测。资源包与显式字段同时填写时，显式字段必须精确对应包内成员；冲突会拒绝。共享三维面板需要完整资源包。旧 `launch_gui` 字段可被配置解析器读取，但工作台统一使用 `hand_service.launch.py`，不再启动外部旧标定窗口。

纯触觉模式使用触觉 profile 的 `resources`。对应动捕 profile 不存在，或明确禁用而触觉启用时，共享面板只展示静态手形与实时触觉，不创建 IMU 控制器、动作示范或掌倾推算，也不报告有效动捕姿态。纯触觉无需数值 Python；旧的无资源矩阵配置仍有效，三维页面会提示配置显示资源。启停仅作用于触觉进程组。动捕与触觉均启用时继续使用同一手的动捕资源，候选预检拒绝两者资源冲突。

触觉设备身份在后台读取 USB 枚举信息，并绑定到当前有效连接的会话/epoch。先打开页面再连接设备也能保存参考；同一路径换设备会隔离旧参考，迟到的旧身份结果不会应用到新连接。此过程不扫描串口数据，不重建手部面板或 IMU 标定。

默认发现分别查找本 checkout 的 `.runtime/left-hand` 与 `.runtime/oct29-right`，以及 `.venv-left-hand`、`.venv-right-hand`。可通过 `VT_LEFT_HAND_RESOURCES`、`VT_RIGHT_HAND_RESOURCES` 和对应的 `VT_LEFT_HAND_PYTHON`、`VT_RIGHT_HAND_PYTHON` 指定其他部署目录。发现只是建议；不会自动连接硬件。

工作台 Qt 环境与数值环境分离。`teaching_geometry` 在对应的数值 Python 中生成有限的示范帧，界面在后台读取结果；该子进程不接触设备，不能提交标定或覆盖实时姿态。

部署步骤仍为构建 `ros2_ws`，并执行 `tools/capture_deploy/install.sh` 安装工作台。两手数值环境需安装本分支的 `vt-fsglove12>=0.1.3`，候选工作台需 `vt-capture-console>=0.9.0`、`vt-capture-core>=0.8.0`、`vt-capture-manager>=0.7.0`、`vt-tactile-capture>=0.3.0`。使用 `start_workbench.sh` 保持 ROS 与 Qt 解释器隔离。

## 候选配置迁移与启动

候选入口与常用工作台分离。迁移只读取旧配置，按显式选定的已验证左右手资源包替换手部实现，保留设备端口、启用状态、相机、VIVE、点云和数据输出设置。旧配置可缺少新增的 `rest` 字段，转换成完整资源包配置后才进行新版校验。迁移不会继承 VIVE Hub 自动启动偏好，不启动硬件，也不改历史标定文件。

在当前 checkout 根目录执行一次（资源位置以本地实际部署为准）：

```bash
.venv-capture-console/bin/python -I -m vt_capture_console.backend.candidate_migration \
  --source "$HOME/.config/visiontactile/workbench/workstation.json" \
  --repo-root "$PWD" \
  --hand left "$PWD/.runtime/left-hand" "$PWD/.venv-left-hand/bin/python" \
  --hand right "$PWD/.runtime/oct29-right" "$PWD/.venv-right-hand/bin/python"
```

默认目标是 `~/.config/visiontactile/candidates/<checkout路径摘要>/`，也可明确指定短的私有 `--settings-dir`。目录通过暂存后原子重命名建立，包含原配置备份、迁移报告与新配置。相同来源再次迁移保留候选里的用户编辑；不同来源或资源选择要求另选目录，不能静默覆盖。每个候选的管理器、手部 socket、显示设置、触觉参考与默认手部采样目录均隔离。已明确指定的历史采样输出路径保持原样。

随后使用：

```bash
bash tools/capture_deploy/start_candidate_workbench.sh --check-only
bash tools/capture_deploy/start_candidate_workbench.sh
```

启动入口不会再次导入全局配置。它验证实际启用手的资源与 Python 来源；动捕数值预检载入 MANO 并检查依赖，但不创建控制器或接触串口。纯触觉只验证显示资源。新版界面和管理器只使用独立候选目录，窗口标题显示后台是否已核验。未准备的目录、其他工作树安装的界面或数值环境、旧协议后台均明确失败。

## 控制、状态和并发

工作台 IPC v7 增加 `hand_sessions` 和 `hand.command`。v1–v6 保持原协议，旧客户端不获得手部修改能力。

IPC v8 增加 `software` 身份：源码根目录、Git 提交、运行源码内容摘要与配置路径。管理器启动时冻结身份，修改代码不会让已运行进程冒充新版本。候选客户端优先使用 v9，也接受能证明相同软件身份的 v8。每个修改命令携带期望身份，管理器在执行前核验。正式采集使用 v9。桌面运行时还检查 Unix 对端 PID、实际工作目录及自己的启动记录。v1–v7 的报文保持不变，普通非候选客户端仍可显式协商旧协议。源码更新后必须重新启动候选后台；不能通过伪造窗口版本文字宣称已经更新。

`hand_sessions` 分开报告服务就绪、传感器新鲜度、标定版本和测量姿态有效性。未标定的服务可以是 `ready`，不能因此声称姿态有效。命令必须绑定管理器实例、服务实例、会话和标定版本；执行前再检查绑定，旧页面或排队期间失效的命令不得作用于新会话。

所有修改通过管理器准入，只有当前管理器持有的运行组可以修改。命令队列与回执数量有界；同编号同请求去重，不同请求复用编号会拒绝；超时只表示结果待核实，不自动重复标定。高频显示直接读取只读服务快照，避免将网格数据塞入管理器的设备状态协议。

标定忙碌状态由手部服务发布，与命令完成计数共同绑定；输入快照先到、网格快照后到，也不能产生“命令已完成但仍显示旧空闲状态”的录制准入窗口。采集、拟合、触指优化和未确认命令期间禁止开始新录制。服务超时不会直接解除这个保护；必须收到执行结果或确认所属进程已经结束。

## 触觉格式与历史记录

旧消息 `TactileSampleArray` / `TactileState` 保持定义不变。新版分别使用
`TactileRow44Array`（schema 2）与 `TactileGridState`（schema 3）。逻辑话题名称不变。

新状态携带 20 行源时间，并由完整 20×20 网格产生触觉显示。新 capture plan v3 固定新消息类型；历史 v1/v2 计划继续按旧类型校验其指纹，相机 recipe 和相机 schema 不随之改变。离线读取根据录包的实际类型选择旧 26 字节或新 44 字节解释器，不根据当前默认格式猜测。历史上如有使用旧同名 IDL 写入新 44 字节结构的录包，会明确拒绝，不能伪装为兼容成功。

旧标定文件的来源兼容只针对一个已定位的问题：资源包内的上游源码并非独立 Git checkout，旧版本却把宿主应用 HEAD 记录为上游 HEAD。兼容检查仍要求固定源文件哈希和其他 provenance 一致，不能借此接受被修改的算法、模型、传感器安装或运行依赖。历史文件原件保留。

### 正式录制与边采边看

在录制页选择本次必须采集的手和数据类别。手势采集需要同一手部会话的原始 IMU 与解算姿态。纯触觉采集检查触觉行数据，可以直接使用。现有标定可继续复用。正式双手配置示例位于 `ros2_ws/src/vt_realsense_capture/config/cameras.formal_both_gloves_tactile.yaml`，其中的相机和通道需要与工作站实际配置匹配。

| 观察项 | 如何解读 |
| --- | --- |
| 设备卡片接收 Hz | 管理器收到该话题的消息频率 |
| 录制页各路写入 Hz | 同一录制进程两次采样之间，存储插件完成写入调用的消息数除以时间间隔 |
| 原始 IMU 采样 Hz | 质量报告按每个 IMU 的样本和主机单调时钟计算。一个录制消息可含多个节点、多个样本 |
| 结束后的完整性核对 | 独立读取 MCAP，逐话题比对录制器输入数、存储返回数、MCAP 可读条数与元数据。写入错误、计数差异和缺少关闭证明均有记录 |

实时三维网格可跳过来不及显示的旧帧。手势测量保留自身帧号、源时间和 21 个关节，画面与触觉对时使用实际显示帧的时间。归档随试次保留录制计数文件 `recorder-metrics.json` 和控制器记录 `controller_session.json`；迁移时将它们与同一试次的 `bag/` 一起复制。历史袋缺少录制器计数时，仍可读取已有数据，报告将该段写入过程标为未核验。

正式动捕会比较所选手的实时来源、会话和已加载的标定与手形参考。后台在身份变化时读取配置、参考姿态和标定文件，按运行时摘要核对原件。管理器将核验过的文件存到本地试次目录的 `<trial_id>/hands/` 下，试次元数据包含文件的相对路径与摘要。结束时再比较录制消息中的身份。开始和结束的后台快照各自带有观察时间，采集过程中的滤波器内部状态未随试次保存。回看当时的姿态可直接使用录下的关节数据。

验收目标工作站的稳定 Hz 时，使用相同设备、配置、录制时长和输出盘，分别记录关闭三维预览、日常预览和高显示负载三种工况。比较各节点样本率与最长间隔、各话题写入率与错误数、结束后的回读差异。传感器固件没有提供硬件序号时，记录能够核验的起点是主机解码出的样本。

本轮离线回归使用既有左右手记录。从两份原始记录各取 2,400 条，经过融合、导出、ROS 桥、录制、关闭和 MCAP 读回，逐条核对节点、六轴原始值和状态字节。两份历史 CSV 只保存浮点时间，原始纳秒时间在质量报告中显示未知。另以合成源做六路同时录制，每路 24 条，核对完整 ROS 消息及录制器计数。

在左手 347 帧、右手 349 帧的历史姿态上，关闭预览、正常预览和网格延迟 120 ms 的三组回放均产生相同的 21 点测量结果。两手任一坐标相对完整模型的最大差异低于 0.00000007 m。该对照可用 `tools/fsglove12/scripts/compare_mano_measurements.py` 检查。三组的测量周期测试各约 2.9 秒；目标工作站的 USB、相机、Tracker、点云与目标磁盘仍需共同运行才能测得整机持续录制 Hz。

短时混合负载回归分别关闭、开启管理器预览，在同一块本地磁盘上通过正常控制器录制约 4 秒。双手六路数据和一路 Tracker 各发送 400 条，另发送 120 帧 1280×720 RGB 图像。两组都从 MCAP 读回 2,920 条，逐路数据内容一致。开启预览时做了 32 次 JPEG 转换。该测试使用合成发布源，硬件传输、三相机同时运行和持续写盘还需在目标工作站验证。示例配置基于未压缩相机数据预估磁盘需求，额外数据流可通过 `recording.disk_guard.additional_stream_bytes_per_second` 纳入容量预算。

### 头部相机的双手方块跟踪

在工作台的“标定与离线工具”中选择“双手方块跟踪”。启动头部相机的原始彩色流，按实际连接选择相机名，再点击“开始跟踪”。窗口读取该相机的彩色图及内参。坐标原点在方块中心，输出单位为米，坐标轴相对于彩色相机光学系。内置规格为边长 30 mm、居中的 24 mm AprilTag 36h11，编号 0–5，两块使用相同的面布局。

- **绑定左右手**。两手在画面中分开放置。可以先展示一只手并点击对应按钮，再让另一只手入镜。两只同时可见时，选手后点击对应方块中心圆圈。编码在两颗方块上重复；交叉产生歧义、短时缺测或相机重启时界面会显示失去绑定。再次点击即可恢复。相同方块在相同位置发生不可见的互换，单目图像无法辨别。
- **加载六面布局**。窗口优先显示当前用户配置目录 `visiontactile/hand-cubes/default-30mm.json` 指定的布局，也可手动选择文件。无文件时内置模板仅含已知的 2 号顶面和 5 号正面。实物面序和贴码朝向须一致。一次只展示一颗，选“识别六面布局”后缓慢旋转，保留相邻面同时可见的过渡，六面复核成功后保存。可用同一文件独立复核第二颗。另一种入口是从单方块短视频恢复布局，依据印刷方码与立方体边长比例校验共边和转向，两个分开的帧组必须得到同一结果。
- **标定贴在手背上的方块**。启动头部相机的彩色、深度和帧时序，在跟踪窗口点击“手背标定”。选左手或右手，让该手自然伸平、手背朝向相机，点击“定格画面”。依次点手腕中央、食指指根、小指指根。用当前手套配置的伸平手模核对绿色骨架，对齐后点击“保存并使用”。可以移动头部从另一个角度查看实时叠加。点击位置缺少可靠深度时，可单独重选。腕点取手套表面的可见参考位置，精度受手套厚度和佩戴移动影响。
- **复用结果**。默认安装参数保存在当前用户配置目录 `visiontactile/hand-cubes/wrist-mounts.json`，下次打开会自动加载。重新标定只更新所选手。更换模型、方块布局或手背贴放位置后，核对对应手的安装关系。已有参数也可以通过“选择腕部安装参数”加载。新的标定绑定手别、手模、方块布局与安装变换。相机与手套时序匹配后，跟踪窗口在实拍图像上叠加 21 点动态手形。标定预览的绿色骨架使用伸平参考手模。

在已加载 ROS 工作区的终端，可使用以下入口。ROS 节点与交互窗口二选一启动跟踪。独立运行安装融合还需要相机时序以及所选手的 `GloveState`。视频布局导入命令创建新文件。

```bash
bash tools/capture_deploy/start_hand_cube_viewer.sh
python3 -m vt_capture_manager.optical.video_layout cube.mp4 new-layout.json
ros2 run vt_capture_manager vt_hand_cube_tracking --ros-args -p camera_name:=d436 -p layout_path:=/path/to/layout.json
ros2 run vt_capture_manager vt_optical_hand_fusion --ros-args -p camera_name:=d436 -p mount_path:=/path/to/mounts.json
```

`/hand_cube_tracking/{left,right}/observation` 逐个已处理的图像帧发布方块结果、有效状态和源图像时标。`/hand_cube_tracking/{left,right}/hand_pose` 可分别给出腕部和 21 点两个有效位。它们可以随原始图像与内参录入 MCAP；例如在独立光学验收中使用以下录制命令，按实际相机名称替换 d436。工作台原有正式采集配方仍按已配置的话题录制，打开预览本身不会将这四个新话题加入已有试次。

```bash
ros2 bag record -s mcap /d436/color/image_raw /d436/color/camera_info /d436/frame_timing /gloves/left/state /gloves/right/state /hand_cube_tracking/left/observation /hand_cube_tracking/right/observation /hand_cube_tracking/left/hand_pose /hand_cube_tracking/right/hand_pose
```

#### 联合空间的手部方向验收

头部相机的第一人称视图和联合空间的自由视角应使用同一份带时间戳的手部观测。掌的前方取手腕到中指指根，手背朝向取对应手模的手背法向，各指指尖的实际朝向取末节指骨。相机观察方向取拍摄时的彩色相机光轴。区分手背朝向镜头和指尖指向镜头时，使用相应部位到镜头中心的方向。

1. 使用手背标定保存的安装参数或已知安装参数的底座。首次绑定后，双手自然平放，手背朝上，手腕靠自己、指尖朝前，两拇指相对。从头部相机看实手，将模型腕点、两拇指尖和食指尖叠在原始未镜像画面上，核对位置、左右和掌背。两手在世界坐标中的初始位置应来自此次观测。这个姿势用于核对，可复用原有手指标定。
2. 左右手分别翻掌，再朝镜头指一下食指，检查掌背翻转和末节指向能随真实动作改变。方块遮挡或身份不确定时显示跟踪状态，记录中保留有效性。
3. 双手回到桌面固定位置，保持方块可见并转头。第一人称图像中的手应移动，联合空间中的手应留在原桌面位置。此项需要实物安装参数、已标定的头部相机和 Tracker，以及联合空间的手部显示接入后验证。
